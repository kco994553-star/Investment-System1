The automation provider supplies no platform-level mutual-exclusion guarantee. Event, hourly CI and manual invocations must share **one remote lease**. Every future executing agent must verify an atomic remote acquisition before any owner-branch, STATE, PR-body or comment write; otherwise remain read-only and abstain from writes. Local files, a task title or matching account login do not prove lease ownership.

1. After identifying a real bounded delta/pending action, fresh-read exact owner HEAD `H` and STATE. A live lease held by another run means read-only/stop; do not steal it. Missing/corrupt STATE or unavailable atomic-write capability means write abstention. The initial authorized manual setup is the sole bootstrap exception described below.
2. Prepare an acquisition state commit with **only parent `H`**, one unique `run_id`, UTC acquisition/expiry and TTL30minutes for automated runs (manual runs may use60minutes). Publish owner ref with `force=false`. This is Git's ancestry-based compare-and-swap: competing commits built from the same `H` are divergent, so only the first can fast-forward. Do not request a force update or recreate/rebase the losing lease commit over the winning ref.
3. Verify remote HEAD is the exact acquisition commit and re-read its STATE with matching `run_id`, unexpired expiry and expected parent. Only then is lease acquisition verified. If the non-force update contends/fails, re-read and stay read-only; no output/comment write is allowed from the losing run.
4. Before every remote mutation, fresh-read remote STATE and verify the same unexpired `run_id`. Use the latest owner HEAD as the sole parent of each state/output commit and non-force-update/verify again. A read from before a race is insufficient.
5. Renew before expiry only while remote STATE still names the same `run_id` and its old lease is unexpired. Renewal is another fresh-parent/non-force/verified state commit. A renewal failure, mismatching run_id, expired lease or unverifiable remote state immediately ends write permission. An expired run cannot renew retroactively or publish previously prepared results; it must reevaluate and obtain a new atomic lease.

After meaningful publication/evidence verification, persist exact processed input identity and pending disposition, then release only the same held run's lease using a fresh-parent/non-force verified commit.
