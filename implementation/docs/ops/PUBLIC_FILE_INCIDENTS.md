# 공개 파일 사고 기록 (Main, 2026-11-22 시작)

공개 Pages 파일이 사라지거나, 이력이 끊기거나, 잘못된 내용으로 게시된 일을 적는다. 항목마다 시각, 원인, 수정 PR, 남은 위험을 적는다.

## 1. macro-evidence.json 이력 초기화 7회 (2026-10-25 ~ 2026-11-22)

- **증상**: 발표 기록과 수집 시작 시각이 0부터 다시 쌓였다(`continuity=BASELINE`, `previous=LOADED`).
- **횟수와 시각(UTC)**: 실행 기록 55회 전부를 읽어 셌다. 첫 생성은 2026-10-21 00:36(실행 19)이고, 그 뒤 초기화가 7회 있었다. 7회 모두 바로 앞 실행이 `MACRO_EVIDENCE BUILD_FAILED`였다.

|---|---|---|
| 24 | 2026-10-25 10:52 | 23 (10-25 00:19) |
| 29 | 2026-10-29 12:13 | 28 (10-29 01:47) |
| 34 | 2026-11-03 03:28 | 33 (11-02 01:29) |

- **원인 1 (계산)**: 원천(BEA·G.17·SLOOS·BTS)이 공개 창보다 긴 기간을 돌려준다. 창 밖 기간은 직전 관측(`obs`)에 없으므로, 실행마다 같은 옛 기간 약 2,200개가 FIRST 발표로 다시 기록됐다(실행당 약 490 KB). 오너가 보관한 2026-11-22 02:14 파일로 대조했다: 발표 기록 6,600건은 2,200개 기간(1919-01~2014-10)이 3번씩 반복된 것이고, 새 발표는 0건이었다.
- **원인 2 (게시)**: 기록이 약 6,600건이 되면 다음 실행에서 파일이 크기 한도(1.8 MB)를 넘어 build가 실패한다(`MACRO_EVIDENCE_TOO_LARGE`). 그때 오프라인 빌드가 먼저 써 둔 빈 자리표시 파일(NOT_COLLECTED)이 그대로 게시됐다. 다음 실행은 그 빈 파일을 정상 사본으로 읽고(`LOADED`), 생성 시각이 없으니 처음부터 다시 시작했다.
- **수정**: #613 (`0048083a` → 병합 `d35a4a31`, 2026-11-22)
  - 창 안에 남는 기간만 발표 기록이 된다.
  - build가 실패하면 검증된 게시본을 바이트 그대로 유지한다(빈 파일을 게시하지 않음).
  - 이어받기 일반 규칙: 문구·형식이 바뀌어도 계열·기록·사건은 이어받는다. 이력을 다시 시작하는 조건은 NO_LIVE / PREVIOUS_UNAVAILABLE / PREVIOUS_DISCARDED / PREVIOUS_PLACEHOLDER 넷뿐이다.
  - 초기화하면 파일의 `resets` 칸에 시각·사유가 남고, 실행 요약에 GitHub 경고가 뜬다.
- **복원**: 하지 않았다(오너 2026-11-22). 2026-11-22 02:14 파일에는 실제 발표 기록이 없었고, 그 산출물의 만료(2026-11-23 02:25 UTC)를 그대로 두었다.
- **남은 위험**: 게시본을 받지 못한 실행(PREVIOUS_UNAVAILABLE)은 새로 시작한다. 다만 이제는 기록과 경고가 남는다.
