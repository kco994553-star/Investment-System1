## 2. Why a method/profile binding is necessary

M1–M5 define principles but do not identify the evidence a specific factor
requires, which subject/profile is economically eligible, or which output a
consumer may use. The same field can be optional for one explicitly authorized
method and necessary for another; the G horizon and EPS fallback issues already
demonstrate that method meaning controls input requirements. A principle-only
runtime would have to guess these bindings and would thereby create policy.

The minimum future binding is a **reference manifest**, reusing stable factor IDs,
existing ProfileKind/Personal immutable weight/configuration objects and versioned
method references. It is not a new ProfileConfig class, independent weight engine,
mutable defaults store or a silently filled factor registry.

| Binding surface | Minimum evidence/reference needed | Present boundary |
|---|---|---|
| Method/factor identity | Existing factor ID; exact immutable meaning, normalization, calculation and supported profile references | No factor meanings or versions are changed by principle approval |
| Requiredness | Approved method/profile role for each relevant factor/input; conditional dependency predicate if any; scope and authority | Existing 20 factors are not assigned roles by this task; unknown is not a default role |
| Applicability | Exact authorized subject/profile predicate, evidence inputs, effective dates and resolution of conflicting N/A claims | Financial ROIC's existing behavior is characterized; no new N/A taxonomy or automatic future denominator rule is approved |
| Admission and failure scope | Existing reason/state evidence; consumed-dependency graph; PIT/provenance/version/identity/finite-value boundary; method-specific quality-resolution references | Preserving failure distinction does not select every STALE/ESTIMATED/CONFLICTING or IDENTIFIER_CHANGED admission rule |
| Planned denominator | Exact eligible scoring set, pinned weight/configuration reference, authorized N/A/zero treatment and arithmetic/version reference | Ordinary missing must not induce available-only reweight; actual denominator binding remains unresolved |
| Output and consumer admission | Explicit meaning of diagnostic, complete, comparable and Official-valid outputs; consumer-specific permitted use and authority | No all-active completeness criterion, partial ranking rule, threshold or promotion is inferred from M4 |
| Namespace and configuration | Existing Official/Personal identities; immutable registry/version/override refs; authorized editable nodes and factor-node binding | Official requirements and validity cannot be modified by Personal overrides; runtime adapter remains excluded |
| Temporal provenance | Subject/source/vintage/calculation/configuration refs; decision time; available_at and published_at evidence under existing protections | Latest/fetched/calculated time cannot replace missing historical availability |

Every field above is a **required design reference**, not an assigned policy
value. A missing binding cannot be completed by inheriting an older simulation's

distinct from missing company evidence. How a future public runtime represents
that distinction remains a separately authorized interface decision.

  no approved metadata formula or normalization is inferred.

  weights and output/consumer rules. Current Q/G total remains the baseline.
- **WeightOverride:** resolve C-24/C-30-equivalent registry authority and exact

The new contract can therefore be designed before G/V semantic replacement is
settled, while an affected method's runtime binding may remain blocked by those
unresolved meanings. Design progress and activation readiness are different
