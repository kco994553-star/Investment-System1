### 다운로드가 업로드 때문에 멈추지 않게 하는 설계

조각 하나가 다 차면 읽기 루프는 그 파일을 백그라운드 업로드 스레드의 큐에 넣기만 하고, 바로 다음 블록을 읽는다.
업로드 스레드는 조각마다 차례로 다음을 한다.

1. 디스크에서 스트리밍해 업로드한다.
2. 스트리밍으로 되받아 SHA-256과 크기를 비교한다 (디스크 0 바이트).
3. 로컬 사본을 지운다.

디스크 예산(4절)은 업로드가 하나도 끝나지 않아도 모든 조각을 담을 수 있게 잡았다. 그래서 읽기 루프가 업로드를 기다릴
일이 없고, curl 저속 제한은 실제 원천 정체에서만 걸린다. 업로드 오류는 다음 블록을 읽기 전에 확인하고, 오류가 있으면
즉시 curl을 끊는다.

## 4. 디스크 (B) — 가정이 아니라 계산

| 항목 | 최대 바이트 | 비고 |
|---|---|---|
| 써 두었지만 아직 업로드·검증·삭제되지 않은 조각 | ≤ S (본문 크기) | 업로드가 전부 멈춰도 이 값을 넘지 않는다 |
| 조각 검증용 다운로드 1개 | 예산 ≤ 1e9, 실제 0 | 되받기는 스트리밍 해시라 디스크에 쓰지 않는다 |
| 재조립 검증 | 0 | 스트리밍, 실물 파일 없음 |
| 작은 파일 (기호 목록) | 수백 바이트 | |
| **최대 사용량 (예산)** | **≤ S + 1e9** | 실제 최대값을 `disk.peak_bytes`로 manifest에 남긴다 |

| 점검 시점 | 조건 | 상수 |
|---|---|---|
| 첫 원천 GET 전 | 여유 ≥ `BODY_CAP` + `CHUNK_BYTES` + `DISK_RESERVE` = 20e9 + 1e9 + 1e9 = **22e9** | `MIN_FREE_BEFORE_SOURCE` |
| 메타데이터(GET 2) 후 | 여유 ≥ S + `CHUNK_BYTES` + `DISK_RESERVE` = **S + 2e9** | |
| 조각 파일을 새로 열 때 | 여유 ≥ min(1e9, 남은 바이트) + 1e9 | `DISK_RESERVE` |

- 여유 공간은 조각 디렉터리(`<workdir>/chunks`) 자체에서 잰다. 작업 디렉터리와 같은 파일시스템(`st_dev`)인지 먼저 확인하고, 다르면 `DISK_PATH_MISMATCH`로 멈춘다.
- 시험: 업로드를 본문 끝까지 묶어 둔 가짜 저장소로 돌렸다. 최대 사용량은 S + 기호 파일 크기와 정확히 같았고, S + 1e9 이하였다. 두 점검은 경계값에서 통과하고, 경계값 − 1에서 거부된다.

  - 그 밖의 자산과 릴리스 자체는 절대 지우지 않는다.
  - FAILED manifest에는 자산마다 `deleted` true/false와 출처(`UPLOAD_ANSWER` / `LISTED_LOST_ANSWER`)를 적는다.

## 6. 재조립 검증 (C) — 스트리밍, 실물 파일 없음

- 업로드한 조각을 순서대로 다시 내려받는다. 그 흐름을 SHA-256, MD5, 바이트 수 계산과 `gzip -t`(파이프 입력)에 동시에 넣는다. 결과는 manifest의 `reassembly: {mode: 'STREAMING_NO_FILE', bytes, sha256_match, md5_match, gzip_test_ok}`다.
- **이번 실행에서는 전체 파일을 물리적으로 다시 합치지 않는다.** 그러려면 S 바이트가 더 필요하다.
- 나중의 재생(예: #501 전체 기호 방식)도 같은 방식으로 조각을 순서대로 스트리밍해 읽으면 된다 (`part-01` … `part-MM`을 이어 붙인 흐름 = 원본).

| **원천 수신 완료** | manifest `received.completed_at_utc` = 파생 `acquired_at_utc` | 모든 바이트를 받았고 size·md5·gzip·parser 검증까지 끝난 시각. **이것이 취득 시각이다** |
| 조각 보존 완료 | manifest `chunks_preserved_at_utc` | 모든 조각의 업로드와 되받기 검증 완료 |
| 재조립 검증 완료 | manifest `reassembly.verified_at_utc` | 스트리밍 재조립 검증 완료 |
| 파생 생성 | 파생 `generated_at_utc`, manifest `derived.generated_at_utc` | |
| manifest 작성 | manifest `written_at_utc` | |

잡 전체가 끝난 시각은 취득 시각으로 쓰지 않는다. manifest는 파생 자산의 이름, SHA-256, 바이트 수를 적고, 파생 파일은
manifest 이름과 원본 SHA-256을 적어 서로 연결한다.

**남은 단계 (이 작업에서 하지 않음):** `financial-v-price-input/1`과 basis 증거는 Codex가 만든다. 계약상 quote의
`share_basis`는 분자(EPS 또는 장부)의 기준과 같아야 한다. basis 레코드도 S를 덮는 `valid_from`/`valid_to`와
`action_status=MATCHED_TO_NUMERATOR`가 필요하다. 이것은 IEX 하루 파일에서 나오지 않으므로, 클래스·기업 행위 근거와 함께
Codex가 만든다.

**Codex 인계 계약(11/06 3차):** 필드·단위·상태·시각 표와 도구가 쓴 합성 예시는 [IEX_DAY_FINANCIAL11_CONTRACT_20261106](IEX_DAY_FINANCIAL11_CONTRACT_20261106.md), 예시 `tests/fixtures/iex_day_financial11_examples_v1.json`(시험이 도구 출력과 같음을 확인).

## 9. 실패 정책과 로그 (D, E)

어떤 실패든 다음 순서로 처리한다. 실패의 예는 HTTP 상태, 크기 상한, size/md5 불일치, gzip/parser 오류, 끊긴 스트림,
조각 업로드·검증 실패, 재조립 불일치, 비공개 읽기 실패, 디스크 점검, 시간 초과 `DEADLINE_EXCEEDED`, 취소 신호
`CANCELLED`다.

1. 즉시 중단한다. 원천 요청을 더 하지 않고, curl·gzip·parser를 종료하고 회수한다.
2. 로컬 조각과 기호 파일을 지운다.
3. 5절의 규칙대로 이번 실행의 자산만 지운다.
4. 비공개 저장소에 닿으면 `manifest-<id>.json`(state `FAILED`)을 올린다. 단, 거부한 릴리스(2단계)에는 쓰지 않는다.
5. 종료 코드는 1이다.

로그 규칙:

- 공개 로그에는 고정 코드, 개수, 크기, 해시, HTTP 상태 코드, 종료 코드, 예외 **클래스 이름**만 남는다. 다른 값은 `REDACTED`로 바뀐다.
- 응답 본문, 예외 메시지, URL, 토큰, 가격, 기호, 코드, CIK는 남지 않는다. 비공개 전송 예외는 `PRIVATE_TRANSPORT_FAILED`로 바꾸고 본문은 버린다.
- 워크플로에는 `set -x`가 없다.
- 시험: 모든 단계에 실패를 하나씩 넣었다. 응답 본문과 예외 메시지에 가격·기호·토큰을 심은 경우도 포함했다. 그 뒤 stdout·stderr 전체에서 소수 가격, 합성 기호·코드·CIK, `Authorization`, `token`, `{`, 응답 본문 표지가 없음을 확인했다.

도구 자체 마감은 125분, 스텝 마감은 140분, 잡 마감은 150분이다.

## 12. 실행 절차 (소유자 승인 후에만)

1. 소유자가 이 문서의 예산을 승인한다: 원천 GET 3회, 20e9 상한, 디스크 계산, 비공개 요청 수.
2. 승인된 커밋에서 `run/iex-20261102-once` 브랜치를 만들어 push한다. 다른 트리거는 없다.
3. 실행이 끝나면 (성공이든 실패든) 먼저 아래 보존을 확인한다.
   - Actions 실행 ID(run id·attempt)와 실행한 코드의 전체 커밋 SHA를 기록했다 (manifest의 run id와 일치).
   - 비공개 릴리스에 `manifest-<id>.json`(COMPLETE 또는 FAILED)이 있고, 성공이면 조각 전부와 파생 파일의 해시가 manifest와 일치한다.
   - 재현 코드(그 커밋)가 실행 가지 밖에서도 남아 있다: 같은 SHA가 준비 가지 `claude/iex-20261102-preserve-prep`(PR #502)에 있다.
4. 위 확인이 끝난 뒤에만 `run/iex-20261102-once` 브랜치를 삭제한다. 다시 시도하려면 새 승인이 필요하다. 이전 시도의 FAILED manifest는 남아 있어도 되고, 새 시도는 다른 이름을 쓴다. COMPLETE가 있으면 다시 실행하지 않는다.
5. 결과 확인: `manifest-<id>.json`의 state가 `COMPLETE`인지, 로그 마지막 줄의 `source_get=3`을 본다.
