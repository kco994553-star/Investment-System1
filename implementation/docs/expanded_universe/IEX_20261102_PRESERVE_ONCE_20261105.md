### 다운로드가 업로드 때문에 멈추지 않게 하는 설계

조각 하나가 다 차면 읽기 루프는 그 파일을 **백그라운드 업로드 스레드의 큐에 넣기만 하고** 바로 다음 블록을 읽는다.
업로드 스레드는 조각마다 순서대로 다음을 한다.

1. 업로드: 디스크에서 1 MiB씩 스트리밍하고, 보내는 바이트의 SHA-256을 함께 계산한다.
2. 검증: 같은 자산을 다시 스트리밍으로 내려받아 SHA-256과 크기를 비교한다.
3. 정리: 로컬 사본을 지운다.

본문이 20 GB 이하이고 사전 점검에서 25 GB 이상 비어 있음을 확인했으므로, 업로드가 하나도 끝나지 않아도 모든 조각이
디스크에 들어간다. 그래서 읽기 루프는 업로드를 기다릴 이유가 없고, curl 저속 제한(1 MiB/s × 60초)은 실제 원천 정체에서만
걸린다. 업로드 쪽 오류는 다음 블록을 읽기 전에 확인한다. 오류가 있으면 즉시 curl을 끊는다(원천 추가 요청 없음).
조각 파일을 새로 열 때마다 「남은 조각 크기 + 1 GB」만큼 여유 공간을 다시 확인한다.

## 3. 요청 예산

| 구분 | 성공 시 | 실패 시 추가 | 비고 |
|---|---|---|---|
| **원천 GET (IEX/GCS)** | **3** (색인 1, 메타데이터 1, 본문 1) | 0 (실패 단계 이후로는 0) | 무료. 재시도, Range, 재개, 다른 날짜 없음. `SourceClient`가 4번째 요청과 같은 종류의 반복 요청을 막는다 |
| 비공개 읽기 (contents API) | 2 | 0 | manifest.json, connected-final.json |
| 비공개 릴리스 조회/생성 | 1 + (없으면 생성 1) | +1 (실패 정리 때 자산 목록 1회) | |
| 비공개 업로드 | N + 2 (조각 N, 파생 1, manifest 1) | +1 (FAILED manifest) | |
| 비공개 다운로드 | 4N (조각 검증 N회 + 재조립 N회, 회당 API 1 + 리다이렉트 1) | 0 | 리다이렉트에는 토큰을 붙이지 않는다 |
| 비공개 삭제 | 0 | 이번 실행이 올린 조각, 파생 파일, manifest 수만큼 | |

N은 크기 ÷ 1e9를 올림한 값이다. 2026-10-23 파일(13,079,032,608 바이트)과 비슷한 크기라면 N = 14이고, 성공 시 업로드 16회,
다운로드 56회다. 상한(20 GB)이면 N = 20이고, 업로드 22회, 다운로드 80회다. 실제 횟수는 manifest의 `requests`와 마지막 로그
줄 `IEX_PRESERVE REQUESTS …`에 원천과 비공개를 나누어 남긴다.

## 4. 저장 구성 (비공개 릴리스 `current-iex-20261102`)

| 자산 | 내용 |
|---|---|
| `iex-tops16-20261102.pcap.gz.part-001` … `-0NN` | 원본 gzip 바이트를 그대로 잘랐다 (1,000,000,000 바이트, 마지막만 작음). GitHub 자산 한도 2 GiB 미만이다. 순서대로 이어 붙이면 원본이 된다 |
| `iex-20261102-financial11-last-trade.json` | 파생 결과 (비공개 전용, 11행) |
| `manifest.json` | 완료 기록, 아래 필드 |
| `manifest-FAILED-<UTC>.json` | 실패 시에만 생긴다 |

`manifest.json`에 남는 필드:

- 원천 URL 3개, 색인 size, 메타데이터 size·md5, 받은 바이트 수, md5, sha256
- 조각 목록 (이름, 크기, sha256)
- parser 소스 SHA-256, 바이너리 SHA-256, git 커밋, 컴파일러, python 버전
- 기호 필터 목록 SHA-256 (목록 자체는 남기지 않음)
- 비공개 입력 영수증 (커밋, 경로, manifest/파일 SHA-256, git blob sha1, 행 번호)
- 세션 창 ns (09:30–16:00 New York)
- parser `#STATS` (packets, segments, messages, trades, bad)
- 상태별 행 수, 완전성 플래그 (size·md5·gzip·parser·curl·조각 검증·재조립), 단계별 소요 시간
- 요청 횟수, state `COMPLETE`

파생 파일은 코드마다 한 행이다. 행 필드:

- `code`, `iex_symbol`
- `state`: `PRICE`, `NO_TRADE`, `NOT_IN_FILE`, `PRICE_INVALID` 중 하나 (+ `reason`)
- `price`: USD/주, 소수 4자리 문자열
- `last_trade_ns` / `last_trade_utc`: 정규장 라운드 로트 마지막 체결 시각
- `basis_date` `2026-11-02`
- `source` `IEX_HIST TOPS 1.6 last regular-session trade` (종가·OHLCV 아님)
- parser SHA-256

상태 판정:

| 상태 | reason | 조건 |
|---|---|---|
| `PRICE` | 없음 | 홀수 로트 플래그와 장외 플래그가 없는 정규장 마지막 체결, 가격 범위와 시각 정상 |
| `NO_TRADE` | `ODD_LOT_ONLY` | 홀수 로트 체결만 있음 |
| `NO_TRADE` | `NO_REGULAR_SESSION_ROUND_LOT_TRADE` | 정규장 체결 없음 |
| `NOT_IN_FILE` | `SYMBOL_NOT_IN_FILE` | 그 날 파일에 디렉터리·상태·체결 메시지가 전혀 없음 |
| `NOT_IN_FILE` | `IEX_SYMBOL_NONE_FROM_ALIAS_DATE` | 별칭표상 IEX 거래 없음 |
| `PRICE_INVALID` | `PRICE_OUT_OF_RANGE`, `TIMESTAMP_OUTSIDE_SESSION`, `IEX_SYMBOL_INVALID` | 가격 범위, 시각, 기호가 유효하지 않음 |

가격이 없거나 무효이면 이유만 남긴다. 다른 날짜나 다른 기호의 가격으로 채우지 않는다.

## 5. 실패 정책

어떤 실패든 (HTTP 상태, 크기 상한, size/md5 불일치, gzip/parser 오류, 끊긴 스트림, 조각 업로드·검증 실패, 비공개 읽기
실패, 디스크 사전 점검, 시간 초과 `DEADLINE_EXCEEDED`, 취소 신호 `CANCELLED`) 다음 순서로 처리한다.

1. 즉시 중단한다. 원천 요청을 더 하지 않고, curl·gzip·parser를 종료하고 회수한다.
2. 로컬 조각 파일과 기호 파일을 지운다.
3. 이번 실행이 올린 자산을 **모두 삭제**한다 (조각, 파생 파일). `DELETE /releases/assets/{id}`를 `raw_store_release.http`와 같은 방식으로 호출한다. 응답을 잃은 업로드도 남을 수 있으므로, 이번 실행이 빈 릴리스를 확인한 뒤라면 자산 목록을 한 번 읽어 우리 이름 규칙의 자산을 함께 지운다. 비어 있지 않아 거부한 릴리스는 건드리지 않는다.
4. 비공개 저장소에 닿을 수 있으면 작은 `manifest-FAILED-<UTC>.json`을 올린다 (state `FAILED`, `failed_stage`, 올렸던 조각 목록과 각각의 삭제 여부, 요청 횟수). 부분 원본이 완성본처럼 남지 않는다.
5. 종료 코드는 1이다.

도구 자체 마감은 125분, 스텝 마감은 140분, 잡 마감은 150분이다. 마감 전에 도구가 스스로 실패 처리와 정리를 끝내도록
여유를 두었다.

로그에는 고정 코드, 개수, 크기, 해시만 남는다. 다른 값은 `REDACTED`로 바뀐다.

## 7. 해결되는 것 (조건부)

- 11개 재무 후보 코드의 **2026-11-02 같은 날 IEX 가격 입력**. IEX 정규장 마지막 체결가이며 공식 종가가 아니다.
- 이 값은 조건부 입력이다. **채택이 아니다.** 공식 계산, 순위, 공개 게시에는 별도 승인이 필요하다.
- 같은 날 원본 전체가 비공개로 보존된다. 그래서 나중에 전체 기호 parser로 같은 원본을 다시 재생할 수 있다.
