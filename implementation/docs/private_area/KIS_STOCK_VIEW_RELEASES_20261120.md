## 3. 종목 하나를 열 때 (수정본 기준 계산)

| 항목 | 값 |
|---|---|
| Worker 하위 요청 | 약 5회: 요청 제한 확인 2, 목록 1, 릴리스 파일 API 1, 넘김 1 (한도 50) |
| GitHub API 호출 | 2회: 목록, 릴리스 파일 |
| 최악의 GitHub 요청량 | 분당 상한 12회 × 2 = **시간당 1,440회** (읽기 토큰 한도 5,000) |
| Worker 쪽 보관(캐시) | 필요 없음 → 넣지 않는다 |
| 해석하는 크기 | 종목 파일 하나(합성 추정 5년 최대 293 KB, 압축 69 KB. **실제 자료(11/21 점검): 최대 344 KB, 압축 140 KB**) + 목록 1개. 11/21 가벼운 판독(#585) 뒤로는 Worker가 풀지 않고 화면이 푼다 |

- **목록이 필요한 이유:** 릴리스 파일은 번호로만 받을 수 있다. 목록에는 종목 → 파일 번호·이름·크기·sha256, 릴리스 태그, 세대가 들어 있고, Git 자료 가지에 하루 한 번 덮어쓴다.
- **목록의 저장 증가 (Codex 답, #437 11/20 → 11/21 정정):** 기존 94 MB에는 들어 있지 않았다. 처음 답은 하루 약 32 KB·첫해 약 207 MB·이후 연 약 102 MB였다. **11/21 정정:** 번호표에 압축 해제 후 크기와 SHA가 들어가 하루 약 61 KB가 되어 **첫해 약 214 MB, 이후 연 약 109 MB**다. 기준 안이다(첫해 1 GB, 이후 연 300 MB). 조회본 형식과 복구 명령은 그대로다.
- **CPU 10 ms 한도와 실제 여는 시간:** 3단계의 실측으로 확인한다. 아직 재지 않았다.

## 4. 매일 갱신 설계 — 세대와 정리

**세대.** 거래일마다 릴리스를 하나 만든다(종목 파일 517개 + QGV 1개). 이름에는 내용 해시를 넣는다. 그러면 한 릴리스의 파일은 늘 518개이고, 한도 1,000개 안이다.

**릴리스는 그 세대 파일을 모두 갖는다.** 바뀌지 않은 종목 파일도 새 릴리스에 다시 올린다. 그래야 세대 하나를 릴리스 하나 단위로 지울 수 있다. Git 원본에서 날마다 전체를 다시 만들므로(`restore`) 옛 세대를 내려받을 필요가 없다.

**하루 순서 (올리기 시간대)**
0. 그날 받은 100거래일 페이지는 실행기 임시 폴더에만 둔다. `append`가 새 행과 원문 해시만 Git 일지에 더한다. 겹치는 원문은 Git에 두지 않는다(11/17 B2, 11/19 세 번째 안). 이 연결은 매일 쓰는 요청 파일을 만드는 방법(Codex #437 Q1)이 정해진 뒤에 만들고, 그 전에는 매일 자동 수집을 켜지 않는다.
1. 새 세대를 새 이름으로 올린다.
2. 목록의 sha256으로 확인한다.
3. 목록 파일을 커밋해 한 번에 바꾼다. Worker는 이 커밋부터 새 세대를 읽는다.
4. 실패하면 목록을 바꾸지 않는다. 그러면 전날 세대가 그대로 쓰인다.

**정리 (올리기와 다른 시간대의 별도 단계)**
- **지우는 방법:** 파일을 하나씩, 간격을 두고 지운 뒤 빈 릴리스를 지운다. 502가 나면 다음 실행에서 다시 한다.
- **요청 수 한도:** 올리기 517회와 지우기 517회를 같은 시간에 하면 `GITHUB_TOKEN`의 시간당 1,000회 한도를 넘는다. 그래서 정리는 다른 시간대에 돈다.
- **지우지 않는 것:**
  - **목록이 가리키는 세대**
  - **바로 전 세대 하나** (되돌리기용)
- **실패해도 멈추지 않는다.** 정리가 실패해도 그날의 갱신과 화면 읽기는 계속된다. 정리 실패는 실행 요약에 적는다.
- **세대가 쌓이면 경고한다.** 남은 세대가 **3개를 넘으면** 실행 요약에 경고를 띄운다.

**되돌리기.** 목록 파일 커밋을 `git revert`로 되돌린다. 바로 전 세대가 남아 있어서 곧바로 원래대로 돌아간다. force push는 쓰지 않는다.
