## 3. 대안

### 3-1. 목록 나누기 (어느 안에서도 필요)
- 목록을 해시 버킷 64개로 나눕니다(버킷당 약 88줄, 약 28 KB).
- Worker는 요청 종목의 버킷 하나만 읽습니다.
- 해석은 약 0.25 ms(로컬 V8 비례 추정)입니다. 새 실행 환경 첫 요청 예상은 모듈 적재 약 2.3 ms를 포함해도 3~4 ms로, 10 ms 안입니다.
- 버킷 파일을 Git에 두면 이력이 여전히 연 약 650 MB입니다. 그래서 Git에는 세대 포인터 하나만 둡니다. 포인터는 약 5 KB이고 버킷 64개의 크기와 sha256을 담으며, 연 약 2 MB입니다. 버킷 자체는 조회본과 같은 곳에 둡니다.

## 3-4. R2 안 — 전제·안전장치·되돌리기 (오너 2026-11-22 추가 지시)

### 전제 (Cloudflare 문서 확인, 2026-11-22)
- **R2 구독이 필요합니다.** 공식 「Get started」는 "You need a Cloudflare account with an R2 subscription"이라고 적고 있습니다.
- **결제 수단 등록이 필요합니다.** 공식 커뮤니티(2026-08)에 따르면 무료로 쓰더라도 「Add R2 subscription」에서 카드 입력 창을 건너뛸 수 없습니다. 이 부분은 공식 문서 본문이 아니라 커뮤니티 답변입니다.
- **한도를 넘으면 자동으로 과금됩니다.** 같은 커뮤니티 답변은 "The usage is not capped"라고 하고, 공식 가격표는 무료분을 넘는 사용량에 아래 단가를 매깁니다.
  - 저장 $0.015 / GB-월
  - 쓰기(Class A) 100만 번당 $4.50
  - 읽기(Class B) 100만 번당 $0.36
  - 삭제와 전송은 무료
- **사용량이 넘을 때 R2를 자동으로 멈추는 기능은 공식 문서에서 찾지 못했습니다.** 그래서 아래 자체 안전장치가 필요합니다.
- **무료분(월)**: 저장 10 GB-월, 쓰기 100만 번, 읽기 1천만 번.

### 오너가 폰에서 할 일 (승인 뒤, 약 10분)
1. Cloudflare 대시보드 → R2 Object Storage → **Add R2 subscription** → 결제 수단 입력
2. **Create bucket**: 이름은 예를 들어 `kis-private-views`로 합니다. 「Public access」는 켜지 않습니다. r2.dev 주소와 사용자 도메인을 모두 연결하지 않습니다.
3. R2 → **Manage API tokens → Create API token**
   - 권한: Object Read & Write
   - 적용 범위: **이 버킷 하나만**
   - 만료일: 예를 들어 1년
4. 발급된 Access Key ID와 Secret을 **비공개 저장소의 Actions 비밀값**에만 넣습니다(`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`). 공개 저장소에는 넣지 않습니다.
5. Billing → Notifications에서 사용량 알림을 켭니다. 계정에서 이 메뉴가 보이는지는 확인하지 못했습니다.
- Worker가 버킷을 읽는 연결(바인딩)은 Main이 배포 설정(wrangler.toml)에 넣습니다. 지금 배포 토큰 권한 목록에 「Workers R2 Storage Write」가 이미 있습니다(`worker/deployment-prerequisites.json`).

### 안전장치
- **비공개 버킷**: 공개 주소를 만들지 않고, Worker 바인딩으로만 읽습니다.
- **쓰기 토큰**: 그 버킷 하나로 범위를 좁히고, 비공개 저장소의 게시 작업 중 올리기 단계 하나에서만 씁니다. KIS 키처럼 한 단계에만 두고, 정적 검사로 고정합니다.
- **사용량 멈춤 장치**: 게시 작업이 이번 달 쓰기 횟수와 저장량을 스스로 셉니다.
  - 올리는 객체 수와 크기는 미리 정확히 알 수 있으므로, 이 값을 비공개 저장소의 작은 장부 파일에 남깁니다.
  - 이번 달 누계에 이번 실행분을 더해 쓰기 80만 번(80%) 또는 저장 8 GB를 넘으면 **올리기 전에 멈추고** `stop=r2_budget`을 남깁니다. 실행이 실패로 표시되므로 오너에게 알림이 갑니다.
  - 이렇게 하면 Cloudflare 분석 API용 토큰이 따로 필요 없습니다.
- **세대 정리**: 지금처럼 활성 세대와 직전 세대만 남깁니다.
  - 정리 작업은 목록에 없는 세대 접두사(`gen/<sha>/`)의 객체를 지웁니다. 삭제는 무료입니다.
  - 버킷 수명 규칙(예: 14일 지난 객체 삭제)을 보조로 둡니다.
- **되돌리기**
  - 517종목 단계에서는 R2와 기존 릴리스에 **함께** 올리는 기간을 2주 둡니다. Worker는 설정 하나로 어느 쪽을 읽을지 고를 수 있게 합니다. 이 기간에 문제가 생기면 설정만 되돌립니다.
  - 2주 동안 문제가 없으면 릴리스 경로를 끕니다.
  - 5,600종목으로 넓힌 뒤에는 릴리스 경로가 요청 한도 때문에 돌 수 없습니다. 그래서 그 뒤의 되돌리기는 "517종목 릴리스 경로로 돌아가기"뿐입니다.

### Worker의 GitHub 읽기 토큰과 릴리스 넘김 예외를 없앨 수 있는가 — 가능, 3단계

| 단계 | 바뀌는 것 | GitHub 읽기 토큰 | 릴리스 넘김 예외 |
|---|---|---|---|
| ① R2 병행 | `/kis/stock`의 조회본과 목록 버킷을 R2에서 읽음. 세대 포인터는 아직 Git(data 가지) | 포인터를 읽을 때 사용 | `/kis/stock`에서 안 씀(기존 릴리스 경로는 되돌리기용으로 남음) |
| ② 포인터도 R2 | 새 세대를 다 올린 뒤 포인터 객체를 마지막에 씀. 원자적 교체 | `/kis/stock`에서 안 씀 | 끔 |
| ③ 옛 경로 정리 | 옛 경로 `/kis/chart`, `/kis/analysis`, `/kis/technical`, `/kis/qgv`(Contents API를 읽는 경로)를 지우거나 R2로 옮김. `/kis/status`의 토큰 만료일 검사도 정리 | **Worker에서 완전히 제거** | **코드에서 제거** |

- ③까지 가면 Worker의 비밀값에서 `PRIVATE_REPO_READ_TOKEN`이 빠지고 넘김 예외도 없어집니다. 둘 다 좁아지는 변경입니다.
- 각 단계는 Worker 배포라서 오너 승인이 필요합니다.

## 3-5. 비교안 — GitHub에 그대로 두고 「월 1회 종목별 + 매일 묶음 64개」

**방식**
- 종목별 5년 부분은 월 1회만 올립니다(종목당 1개).
- 매일은 최근 꼬리(이번 달 행, 지표, 최신 분석)를 해시 버킷 64개 묶음으로만 올립니다.
- Worker는 종목 파일과 그 종목이 든 묶음을 둘 다 넘겨줍니다. 기기가 두 부분을 이어 붙입니다.

| 기준 | R2 (C안) | GitHub 월간 + 매일 묶음 64개 |
|---|---|---|
| 하루 요청 | R2 쓰기 약 5,700번(무료 한도 안). GitHub 요청 수십 번 | GitHub 약 70번(묶음 64 + qgv + 확인). 월 1회 날은 5,600번 → 시간당 1,000번 한도 때문에 **6일 이상에 나눠 올려야 함** |
| 릴리스 자산 수 | 해당 없음 | 월간 세대에 5,600개 → 릴리스 6개 이상 |
| 매일 실행 시간 | 약 2시간 45분(KIS 순차 82분 포함) | 약 2시간 40분. 다만 꼬리만 만드는 생산자가 있어야 하고, 없으면 지금처럼 전체를 만듦 |
| Worker CPU (새 실행 환경) | 목록 버킷 해석 0.25 ms + 조회본 해시 0.3 ms + 모듈 적재 → 약 3 ms | 목록 버킷 + 종목 파일(약 175 KB)과 묶음(약 250 KB, 추정) 두 개의 해시 약 0.7 ms → 약 3.5~4 ms. 넘김을 두 번 거치고, 하위 요청은 5번 |
| 넘김 예외 | 없앨 수 있음(위 3단계) | 유지. 요청 하나에 넘김 두 번 |
| 기기에서 합치는 부담 | 없음(한 파일) | 묶음 하나에 약 88종목의 꼬리가 들어 있음. 약 1 MB JSON을 해석하고 이어 붙이는 검증이 폰에서 약 10~20 ms(추정). 지표는 생산자가 꼬리에 넣어야 함(화면에서 다시 계산 금지) |
| Codex 작업량 | 조회본 형식 변경 없음(목록 나누기는 Main) | **큼**: 조회본을 5년부·꼬리로 나누는 형식, 월 경계 넘김 규칙, 꼬리용 투영, 최신 분석의 위치 이동 |
| Main 작업량 | 버킷·바인딩, 올리기 단계, 정리, 사용량 장부, Worker 읽기 경로 | 월간·매일 두 모드, 6일에 나눠 올리기와 정리, Worker 두 객체 읽기, 읽기 모듈 합치기 |
| 비용 | 무료 한도 안(약 2 GB, 쓰기 월 약 17만 번). 넘으면 자동 과금. 카드 등록 필요 | 0원. 카드 필요 없음 |
| 경계 변화 | 새 저장 위치 1곳과 새 비밀값 1개(넓어짐). GitHub 읽기 토큰과 넘김 예외는 결국 제거(좁아짐) | 없음 |

**권고: R2 (C안)**
- 근거 1: GitHub 안은 월 1회 날에 요청 한도에 걸려 6일 이상에 나눠야 하고, 그 사이 세대가 섞이지 않게 관리해야 합니다.
- 근거 2: GitHub 안은 Codex 쪽 형식 변경이 크고, 폰에서 묶음을 합쳐야 합니다.
- 근거 3: R2는 결국 Worker의 비밀값과 넘김 예외를 줄입니다.
- 대가: 카드 등록과 자동 과금 위험입니다. 이는 자체 사용량 멈춤 장치(80%)로 막습니다.
- **5,600종목 수치(호출 수, 저장량)는 Codex 설계가 오면 그 값으로 고칩니다.** 지금 값은 517종목 실측을 비례로 늘린 추정입니다.

## 3-6. Main·Codex 공동안 (오너 2026-11-22 지시: 같은 점·다른 점을 밝히고 하나로 합침)

**같은 점**
- 두 안 모두 종목 목록을 64개로 나눕니다(3-1). Worker는 요청 종목의 조각 하나만 읽습니다.
- 두 안 모두 오너 인증, 분당 상한, 공개 경계를 그대로 둡니다. 공개 Pages에는 아무것도 가지 않습니다.
- 조회본의 내용과 형식은 그대로입니다(Codex 생산자 형식 변경 없음).

**다른 점: 종목별 조회본을 어디에 두는가**

| | Main 안 (R2) | Codex 안 (비공개 묶음) |
|---|---|---|
| 저장 | R2 비공개 버킷에 종목별 파일 | 이 비공개 저장소의 릴리스에 묶음 파일 64개(묶음당 약 88종목) |
| 하루 올리기 | R2 쓰기 약 5,700번 | GitHub 요청 약 70번(묶음 64 + qgv + 확인) |
| 새 저장 위치·비밀값·비용 | 1곳, 1개, 카드 등록 | 없음, 없음, 0원 |
| Worker가 한 종목을 읽는 법 | R2 바인딩으로 그 파일만 읽음 | 묶음 안의 그 종목 부분만 범위 요청으로 읽음(조각에 시작 위치·길이·sha256 고정) |
| 넘김 예외 | 결국 없앰 | 유지(지금과 같은 한 번) |
| 확인 안 된 것 | 없음(문서 확인) | **release-assets가 범위 요청(Range)을 받는지 미확인.** 안 받으면 Worker가 묶음 전체(약 12 MB)를 받아야 해서 무료 요금제 CPU·메모리로는 불가 |

- 이 표의 「Codex 안」은 「64개 목록 + 비공개 묶음 파일」을 Main이 이렇게 이해한 것입니다. 3-5의 「월간 종목별 + 매일 꼬리 묶음」과 달리 조회본 형식을 나누지 않습니다. 다르면 Codex가 고칩니다.

**공동안 (단계마다 승인)**
1. **목록 64개 나누기 (공통)**
   - 오프라인 시험은 비공개 PR #23입니다. 지금 517종목 목록으로 나누고 다시 붙였을 때 바이트까지 같았습니다. 가장 큰 조각은 5,041 B, 5,600종목 추정은 34,457 B입니다.
   - 그다음 게시 워크플로가 조각도 함께 씁니다. 옛 목록은 그대로 둡니다.
   - 그다음 Worker가 둘 다 읽게 하고, 마지막에 목록을 바꿉니다(3-7 순서).
2. **묶음 가능성 확인 (새 저장소·비밀값 없음)**
   - 이미 올라간 자산 하나에 범위 요청을 1회 보냅니다(게시 작업 토큰). 206과 요청한 길이가 오는지 봅니다.
   - 같은 날 Codex의 5,600종목 측정값(크기, 매일 시간)을 받습니다.
3. **저장 위치 결정 규칙**
   - 범위 요청이 되고 Codex 측정이 GitHub 한도(시간당 1,000번, 릴리스당 1,000개, 작업 6시간) 안이면 **Codex 묶음 안**으로 갑니다. 비용과 새 비밀값이 없습니다.
   - 범위 요청이 안 되거나 한도를 넘으면 **R2 안**(3-4)으로 갑니다. 카드 등록, 비밀값 1개, 사용량 멈춤 장치에 대한 승인이 필요합니다.
   - 어느 쪽이든 1단계의 조각 목록은 그대로 씁니다.

## 3-7. 자료 형식이 바뀌는 게시의 순서 (오너 2026-11-22 지시, 모든 단계에 적용)
- **규칙: 새 형식을 읽을 수 있는 화면·Worker를 먼저 게시하고, 그 뒤에 자료를 바꿉니다.**
- 이번 사례(2026-11-22):
  - 분할 조회본(#593)이 먼저 올라갔습니다. 새 칸(`raw_fields`, 7열)을 읽는 판독기(#596)는 그 뒤에 게시됐습니다.
  - 그 사이 약 30분 동안 분할 종목 33개가 「형식 오류 · TYPE」로 열리지 않았습니다.
- 순서:
  1. 판독기 PR에 옛 형식과 새 형식을 **둘 다** 읽는 시험을 넣습니다.
  2. 판독기(화면은 사이트 게시, Worker는 배포)를 먼저 게시합니다.
  3. 게시된 화면이 **옛 자료로 그대로 열리는지** 폰에서 1종목 확인합니다.
  4. 그다음 자료(조회본, 목록 파일)를 바꿉니다.
- 되돌리기도 같은 순서를 지킵니다. 자료를 먼저 옛 세대로 되돌리고, 판독기는 그 뒤에 되돌립니다.
- 목록 나누기(3-1)와 저장 위치 변경(3-2)도 이 순서를 따릅니다. Worker가 나눈 목록과 옛 목록을 둘 다 읽게 한 뒤 목록을 바꿉니다.
- 후속 검토(지금은 고치지 않음): 이미 열려 있는 옛 탭이 새 자료를 만나 「형식 오류 · TYPE」가 나면 「새로고침해 주세요」 안내를 보일지 검토합니다.

## 5. 확인하지 못한 것
- 5,600종목 수치는 517종목 실측을 비례로 늘린 추정입니다. 실제로 돌려 보지 않았습니다.
- Cloudflare R2 무료 한도와 가격은 공식 가격 문서(2026-11-22 확인) 기준입니다. 결제 수단이 필요하다는 점과 자동 정지 기능이 없다는 점은 공식 커뮤니티 답변 기준입니다. 이 계정에서 직접 확인하지는 않았습니다.
- KIS를 병렬로 받을 때 초당 한도는 문서 기준(18건)입니다. 실측 거부는 약 25건/초에서 났습니다.
