## 3. 대안

### 3-1. 목록 나누기 (어느 안에서도 필요)
- 목록을 해시 버킷 64개로 나눕니다(버킷당 약 88줄, 약 28 KB).
- Worker는 요청 종목의 버킷 하나만 읽습니다.
- 해석은 약 0.25 ms(로컬 V8 비례 추정)입니다. 새 실행 환경 첫 요청 예상은 모듈 적재 약 2.3 ms를 포함해도 3~4 ms로, 10 ms 안입니다.
- 버킷 파일을 Git에 두면 이력이 여전히 연 약 650 MB입니다. 그래서 Git에는 세대 포인터 하나만 둡니다. 포인터는 약 5 KB이고 버킷 64개의 크기와 sha256을 담으며, 연 약 2 MB입니다. 버킷 자체는 조회본과 같은 곳에 둡니다.

## 3-4. R2 안 — 전제·안전장치·되돌리기 (오너 2026-11-22 추가 지시)

### 전제 (Cloudflare 문서 확인, 2026-11-22)
- **R2 구독이 필요합니다.** 공식 「Get started」는 "You need a Cloudflare account with an R2 subscription"이라고 적고 있습니다.
- **결제 수단 등록이 필요합니다.** 공식 커뮤니티(2026-08)에 따르면 무료로 쓰더라도 「Add R2 subscription」에서 카드 입력 창을 건너뛸 수 없습니다. 이 부분은 공식 문서 본문이 아니라 커뮤니티 답변입니다.
- **한도를 넘으면 자동으로 과금됩니다.** 같은 커뮤니티 답변은 "The usage is not capped"라고 하고, 공식 가격표는 무료분을 넘는 사용량에 아래 단가를 매깁니다.
  - 저장 $0.015 / GB-월
  - 쓰기(Class A) 100만 번당 $4.50
  - 읽기(Class B) 100만 번당 $0.36
  - 삭제와 전송은 무료
- **사용량이 넘을 때 R2를 자동으로 멈추는 기능은 공식 문서에서 찾지 못했습니다.** 그래서 아래 자체 안전장치가 필요합니다.
- **무료분(월)**: 저장 10 GB-월, 쓰기 100만 번, 읽기 1천만 번.

### 오너가 폰에서 할 일 (승인 뒤, 약 10분)
1. Cloudflare 대시보드 → R2 Object Storage → **Add R2 subscription** → 결제 수단 입력
2. **Create bucket**: 이름은 예를 들어 `kis-private-views`로 합니다. 「Public access」는 켜지 않습니다. r2.dev 주소와 사용자 도메인을 모두 연결하지 않습니다.
3. R2 → **Manage API tokens → Create API token**
   - 권한: Object Read & Write
   - 적용 범위: **이 버킷 하나만**
   - 만료일: 예를 들어 1년
4. 발급된 Access Key ID와 Secret을 **비공개 저장소의 Actions 비밀값**에만 넣습니다(`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`). 공개 저장소에는 넣지 않습니다.
5. Billing → Notifications에서 사용량 알림을 켭니다. 계정에서 이 메뉴가 보이는지는 확인하지 못했습니다.
- Worker가 버킷을 읽는 연결(바인딩)은 Main이 배포 설정(wrangler.toml)에 넣습니다. 지금 배포 토큰 권한 목록에 「Workers R2 Storage Write」가 이미 있습니다(`worker/deployment-prerequisites.json`).

### 안전장치
- **비공개 버킷**: 공개 주소를 만들지 않고, Worker 바인딩으로만 읽습니다.
- **쓰기 토큰**: 그 버킷 하나로 범위를 좁히고, 비공개 저장소의 게시 작업 중 올리기 단계 하나에서만 씁니다. KIS 키처럼 한 단계에만 두고, 정적 검사로 고정합니다.
- **사용량 멈춤 장치**: 게시 작업이 이번 달 쓰기 횟수와 저장량을 스스로 셉니다.
  - 올리는 객체 수와 크기는 미리 정확히 알 수 있으므로, 이 값을 비공개 저장소의 작은 장부 파일에 남깁니다.
  - 이번 달 누계에 이번 실행분을 더해 쓰기 80만 번(80%) 또는 저장 8 GB를 넘으면 **올리기 전에 멈추고** `stop=r2_budget`을 남깁니다. 실행이 실패로 표시되므로 오너에게 알림이 갑니다.
  - 이렇게 하면 Cloudflare 분석 API용 토큰이 따로 필요 없습니다.
- **세대 정리**: 지금처럼 활성 세대와 직전 세대만 남깁니다.
  - 정리 작업은 목록에 없는 세대 접두사(`gen/<sha>/`)의 객체를 지웁니다. 삭제는 무료입니다.
  - 버킷 수명 규칙(예: 14일 지난 객체 삭제)을 보조로 둡니다.
- **되돌리기**
  - 517종목 단계에서는 R2와 기존 릴리스에 **함께** 올리는 기간을 2주 둡니다. Worker는 설정 하나로 어느 쪽을 읽을지 고를 수 있게 합니다. 이 기간에 문제가 생기면 설정만 되돌립니다.
  - 2주 동안 문제가 없으면 릴리스 경로를 끕니다.
  - 5,600종목으로 넓힌 뒤에는 릴리스 경로가 요청 한도 때문에 돌 수 없습니다. 그래서 그 뒤의 되돌리기는 "517종목 릴리스 경로로 돌아가기"뿐입니다.

### Worker의 GitHub 읽기 토큰과 릴리스 넘김 예외를 없앨 수 있는가 — 가능, 3단계

| 단계 | 바뀌는 것 | GitHub 읽기 토큰 | 릴리스 넘김 예외 |
|---|---|---|---|
| ① R2 병행 | `/kis/stock`의 조회본과 목록 버킷을 R2에서 읽음. 세대 포인터는 아직 Git(data 가지) | 포인터를 읽을 때 사용 | `/kis/stock`에서 안 씀(기존 릴리스 경로는 되돌리기용으로 남음) |
| ② 포인터도 R2 | 새 세대를 다 올린 뒤 포인터 객체를 마지막에 씀. 원자적 교체 | `/kis/stock`에서 안 씀 | 끔 |
| ③ 옛 경로 정리 | 옛 경로 `/kis/chart`, `/kis/analysis`, `/kis/technical`, `/kis/qgv`(Contents API를 읽는 경로)를 지우거나 R2로 옮김. `/kis/status`의 토큰 만료일 검사도 정리 | **Worker에서 완전히 제거** | **코드에서 제거** |

- ③까지 가면 Worker의 비밀값에서 `PRIVATE_REPO_READ_TOKEN`이 빠지고 넘김 예외도 없어집니다. 둘 다 좁아지는 변경입니다.
- 각 단계는 Worker 배포라서 오너 승인이 필요합니다.

## 3-5. 비교안 — GitHub에 그대로 두고 「월 1회 종목별 + 매일 묶음 64개」

**방식**
- 종목별 5년 부분은 월 1회만 올립니다(종목당 1개).
- 매일은 최근 꼬리(이번 달 행, 지표, 최신 분석)를 해시 버킷 64개 묶음으로만 올립니다.
- Worker는 종목 파일과 그 종목이 든 묶음을 둘 다 넘겨줍니다. 기기가 두 부분을 이어 붙입니다.

| 기준 | R2 (C안) | GitHub 월간 + 매일 묶음 64개 |
|---|---|---|
| 하루 요청 | R2 쓰기 약 5,700번(무료 한도 안). GitHub 요청 수십 번 | GitHub 약 70번(묶음 64 + qgv + 확인). 월 1회 날은 5,600번 → 시간당 1,000번 한도 때문에 **6일 이상에 나눠 올려야 함** |
| 릴리스 자산 수 | 해당 없음 | 월간 세대에 5,600개 → 릴리스 6개 이상 |
| 매일 실행 시간 | 약 2시간 45분(KIS 순차 82분 포함) | 약 2시간 40분. 다만 꼬리만 만드는 생산자가 있어야 하고, 없으면 지금처럼 전체를 만듦 |
| Worker CPU (새 실행 환경) | 목록 버킷 해석 0.25 ms + 조회본 해시 0.3 ms + 모듈 적재 → 약 3 ms | 목록 버킷 + 종목 파일(약 175 KB)과 묶음(약 250 KB, 추정) 두 개의 해시 약 0.7 ms → 약 3.5~4 ms. 넘김을 두 번 거치고, 하위 요청은 5번 |
| 넘김 예외 | 없앨 수 있음(위 3단계) | 유지. 요청 하나에 넘김 두 번 |
| 기기에서 합치는 부담 | 없음(한 파일) | 묶음 하나에 약 88종목의 꼬리가 들어 있음. 약 1 MB JSON을 해석하고 이어 붙이는 검증이 폰에서 약 10~20 ms(추정). 지표는 생산자가 꼬리에 넣어야 함(화면에서 다시 계산 금지) |
| Codex 작업량 | 조회본 형식 변경 없음(목록 나누기는 Main) | **큼**: 조회본을 5년부·꼬리로 나누는 형식, 월 경계 넘김 규칙, 꼬리용 투영, 최신 분석의 위치 이동 |
| Main 작업량 | 버킷·바인딩, 올리기 단계, 정리, 사용량 장부, Worker 읽기 경로 | 월간·매일 두 모드, 6일에 나눠 올리기와 정리, Worker 두 객체 읽기, 읽기 모듈 합치기 |
| 비용 | 무료 한도 안(약 2 GB, 쓰기 월 약 17만 번). 넘으면 자동 과금. 카드 등록 필요 | 0원. 카드 필요 없음 |
| 경계 변화 | 새 저장 위치 1곳과 새 비밀값 1개(넓어짐). GitHub 읽기 토큰과 넘김 예외는 결국 제거(좁아짐) | 없음 |

**권고: R2 (C안)**
- 근거 1: GitHub 안은 월 1회 날에 요청 한도에 걸려 6일 이상에 나눠야 하고, 그 사이 세대가 섞이지 않게 관리해야 합니다.
- 근거 2: GitHub 안은 Codex 쪽 형식 변경이 크고, 폰에서 묶음을 합쳐야 합니다.
- 근거 3: R2는 결국 Worker의 비밀값과 넘김 예외를 줄입니다.

## 3-8. Worker의 고정 종목 목록은 5,600종목에서 어떻게 바꾸나 (오너 2026-11-22 지시: 문서만, 지금 코드는 바꾸지 않음)
- 지금 Worker는 받을 수 있는 종목을 코드에 박힌 목록으로 정합니다.
  - `KIS_SYMBOLS` = Universe 목록(`US_SYMBOLS`) + 승인된 ETF 15개(`KIS_ETFS`).
  - 목록에 없는 종목은 자료를 읽기 전에 `REQUEST_INVALID`(400)로 거절합니다.
  - 그래서 종목을 늘리려면 Worker 코드를 고쳐 다시 배포해야 합니다. 5,600종목에서는 이 방식이 맞지 않습니다.
- 바꿀 방식: **「목록에 있는가」를 코드가 아니라 고정된 64개 색인 조각(shard)으로 판단합니다.**
  1. 요청 모양 검사는 그대로 둡니다. `?symbol=` 하나만 받고 `^[A-Z][A-Z0-9-]{0,9}$`만 통과합니다.
  2. 조각 번호는 `sha256(요청 키)[0] >> 2`로 계산합니다. 묶음 경로(#600)와 같은 규칙입니다.
  3. 최상위 파일(`kis-stock-packs.json`)에 적힌 크기와 sha256이 맞는 조각만 읽습니다.
  4. 그 조각의 `stocks`에 종목이 있으면 받습니다. 없으면 `MISSING`(404)으로 답합니다.
  5. 조각 하나는 256 KB 이하입니다(`KIS_PACK_SHARD_MAX_BYTES`). 5,600종목이면 조각당 평균 약 88종목입니다.
- 함께 옮길 것:
  - BRK-B → BRK_B 같은 저장 키 바꾸기(`KIS_STORED_KEY`)를 조각 항목에 적힌 값으로 옮깁니다. 지금은 코드에 2개만 박혀 있습니다.
  - `/kis/chart` 등 종목별 경로도 같은 조각 소속으로 판단합니다.
- 달라지는 점:
  - 목록에 없는 종목의 답이 400에서 404(`MISSING`)로 바뀝니다. 화면에서 두 경우가 모두 「자료 없음」으로 보이는지 판독기 시험에서 먼저 확인합니다.
  - 목록에 없는 종목도 조각 하나(256 KB 이하)를 읽게 됩니다. 분당 요청 상한과 오너 인증이 먼저 걸리므로 둘 다 바꾸지 않습니다. 인증 없는 요청은 지금처럼 조각을 읽기 전에 거절합니다.
- 그대로 두는 것: 로그인, 분당 요청 상한, 넘김 예외(release-assets 한 번, 인증 정보 없이), 가드는 넓히지 않습니다.
- 순서(3-7 규칙):
  1. Worker가 고정 목록과 조각 소속을 **둘 다** 받아들이게 해서 먼저 배포합니다. 517종목에서는 두 판단이 같아야 합니다.
  2. 517종목에서 두 판단이 같은지 시험으로 확인합니다.
  3. 그 뒤 목록을 늘립니다. 고정 목록은 마지막에 뺍니다.
- 묶음 경로가 실제로 켜진 뒤에는 옛 단일 색인으로 돌아가는 경로도 정리 대상입니다. 5,600종목이면 단일 색인이 너무 커집니다.
- 이 변경은 별도 PR로 승인을 받은 뒤 합니다.

- 평소 매일 수집(6,673증권, 종목당 1쪽)이 하루 상한을 넘는 문제는 범위와 상관없이 그대로입니다(6-3의 마지막 줄, 오너 결정 대기).

**1년 종목과 5년 종목이 섞일 때 영향 (한 줄)**
- 조회본 형식이 같아서 Worker(바이트만 넘김)와 화면 모두 고치지 않아도 열립니다.

## 7. 호출 상한을 푸는 방법 (오너 2026-11-22, 설계와 확인만 · 실행은 따로 승인)

지금 확정된 계획(이틀 실행, 전부 1년)은 바꾸지 않습니다. 유료 수단과 새 공급처는 쓰지 않습니다.

### 7-1. 하루 상한 단계적 올리기 (Main 설계 · Codex 예산 검사에 반영 요청)
- **전제**
  - 하루 6,049호출은 KIS 한도가 아닙니다. 11/20에 실제로 성공한 양에 맞춘 우리 안전선입니다.
  - KIS 공식 문서에서 확인한 한도는 초당 호출 수뿐입니다. 하루 한도 문구는 찾지 못했습니다(7-3).
  - 초당 호출 수는 지금 값 그대로 둡니다: 순차 호출, 1호출 약 0.8~0.9초, 초당 약 1.1~1.3건. 문서 한도 18건보다 훨씬 낮습니다. 바꾸는 것은 하루 총량뿐입니다.
- **단계별 상한(제안)**

| 단계 | 하루 상한(토큰·실패·재시도 포함) | 6,049 대비 |
|---|---:|---:|
| L0 | 6,049 | 1.00 |
| L1 | 7,500 | 1.24 |
| L2 | 9,000 | 1.49 |
| L3 | 10,500 | 1.74 |
| L4 | 12,000 | 1.98 |

- L4보다 높은 단계는 만들지 않습니다. 더 올리려면 오너 결정이 필요합니다.
- **세는 법**
  - 같은 앱키로 그날 보낸 모든 요청을 셉니다: 일일 수집, 최근 시세, 5년·1년 채우기, 토큰 발급·폐기, 실패, 재시도.
  - KIS의 날짜 경계를 모르므로, **UTC 날짜와 한국 날짜 두 가지 모두로** 상한 이하여야 합니다.
  - 장부는 #42의 직렬 잠금 안에서 맞춥니다. 실행 전에 「이미 쓴 양 + 이번 계획 + 남은 예약분 ≤ 상한」을 확인합니다. 맞지 않으면 그 구간은 시작하지 않습니다.
- **올리는 조건**: 다음을 모두 만족한 날이 있으면, 그다음 실행일에만 한 단계 올립니다. 단계를 건너뛰지 않습니다.
  - 그날 쓴 양이 그날 상한의 90% 이상이었다. 적게 쓴 날은 근거가 되지 않습니다.
  - 속도 제한 응답(`EGW00201` 또는 HTTP 429)이 0이었다.
  - 재시도가 0이었다.
  - 5xx·연결 오류·시간 초과가 0이었다.
  - 인증 오류(401·403, `EGW00121`·`EGW00123`)가 0이었다.
  - 모르는 응답 코드(`msg_cd`)가 0이었다.
  - 모든 회차가 끝까지 돌았다(취소·시간 초과 없음).
  - 토큰 발급·폐기가 모두 정상이었다.
- **멈추는 조건**(회차 중):
  - 속도 제한 응답이 1건이라도 오면 그 회차를 바로 멈추고 다시 시도하지 않습니다. 이미 받은 페이지는 저장 검사를 거쳐 보존합니다.
  - 모르는 응답 코드가 1건이라도 오면 멈춥니다. 하루 한도 초과를 뜻하는 코드일 수 있습니다.
  - 인증 오류가 1건이라도 오면 멈춥니다.
  - 5xx·연결 오류·시간 초과는 재시도 없이 그 종목만 미응답으로 남깁니다. 한 회차에 3건이 되면 멈춥니다.
- **고정하는 조건**: 어느 단계에서든 속도 제한이 1건이라도 나면, 그 전 단계를 상한으로 고정합니다. 예: L2에서 나면 L1에 고정합니다. 오너가 다시 정할 때까지 올리지 않습니다. 멈춘 구간은 다음 실행일에 고정된 상한으로 이어 받습니다.
- **되돌리는 조건**
  - 속도 제한 없이 5xx·연결 오류가 3건 이상인 날이 이틀 연속이면 한 단계 내립니다.
  - KIS에서 과다 사용 안내(메일·알림·공지)를 받으면 바로 L0으로 돌아가고 오너에게 보고합니다.
  - 모르는 응답 코드로 멈췄으면 그 코드의 뜻을 공식 문서로 확인하기 전까지 L0에 둡니다.
- **올리는 순서 예**: 11/24 1일차는 계획대로 약 4,453호출에 매일 수집 약 519호출을 더해 약 5,000입니다. L0의 90% 이하라서 올리는 근거가 되지 않습니다. 단계를 올리려면 그 단계의 90% 이상을 쓰는 날이 필요하므로, 올리기는 채우기(1년·5년)처럼 양이 큰 날에만 됩니다.
- **구현 위치**(승인 뒤): 비공개 수집 워크플로의 상한 확인 단계와 #42 예산 검사(`two_day_budget`의 6,049를 단계 값으로). 초당 속도와 요청 간격 코드는 고치지 않습니다.

### 7-3. 여러 종목을 한 번에 주는 KIS 조회 (Main, 공식 문서만 · 시험 호출 없음)

출처는 KIS Developers 포털의 API 상세(공식, 2026-11-22 확인)입니다. 주문·계좌·잔고 경로는 보지 않았습니다.

| 조회 | 경로 · tr_id | 한 번에 | 주는 값 | 날짜 지정 | 판정 |
|---|---|---|---|---|---|
| **해외주식 복수종목 시세조회** | `GET /uapi/overseas-price/v1/quotations/multprice` · `HHDFS76220000` | **최대 10종목**(`NREC` "최대 10", `EXCD_01~10`·`SYMB_01~10`). NYS·NAS·AMS를 섞어 요청 가능 | 현재가 `last`, 시가·고가·저가, 거래량 `tvol`, 거래대금 `tamt`, 전일 종가 `base`, 전일 거래량 `pvol`, 상장주수 `shar`, 시가총액 `tomv`, 현지 시각 `xhms` | **없음**(지금 시세 한 장) | **있음.** 매일 갱신에 쓸 수 있음 |

- **원종가 여부**
  - 복수종목 시세는 지금 시세(실시간 무료 시세)입니다. 수정주가라는 문구가 없으므로 원주가로 보지만, 문서가 「원종가」라고 적지는 않습니다.
  - 미국 무료 시세에 대한 공식 문구: 「나스닥 마켓센터에서 거래되는 호가」 기준이고, 「시가, 저가, 고가, 종가는 … 유료 실시간 시세 서비스와 다를 수 있으며」 「종목별 과거 데이터(거래량, 시가, 종가, 고가, 차트 데이터 등)는 장 종료 후(오후 12시경) 유료 실시간 시세 서비스 데이터와 동일하게 업데이트됩니다」.
  - 그래서 장 마감 직후 값은 거래량 등이 통합 시세와 다를 수 있습니다. 「오후 12시경」 뒤(한국 시각 정오로 읽힘, 약 03:00 UTC)에 받아야 통합 값과 같다고 봅니다.
  - **이 문구는 지금의 일봉 수집(01:23 UTC = 한국 10:23)에도 해당할 수 있습니다.** 마지막 하루의 거래량·고저가가 나중에 바뀌는지 Codex 확인이 필요합니다(오늘은 바꾸지 않음).
- **매일 갱신 호출 수**

| 방식 | 6,673증권 하루 호출 | 시간(0.88초/호출) |
|---|---:|---:|
| 지금: 기간별시세 1쪽/종목 | 약 6,673 + 토큰 | 약 98분 |
| 복수종목 시세 10종목/호출 | **약 668 + 토큰** | **약 10분** |

- **대가와 조건**(Codex 7-2 설계에 넘김)
  - 복수종목 시세는 「그날 하루」만 줍니다. 실행이 하루 빠지면 그날 값이 비므로, 빠진 날은 기간별시세(1호출 = 최근 100거래일)로 메워야 합니다. 「매일 복수종목 + 주기적 기간별시세로 대사」가 됩니다.
  - 분할 같은 사건은 복수종목 시세로는 알 수 없습니다. 분할·상장 변경 탐지는 지금처럼 기간별시세 원주가 계열과 마스터 대사로 합니다.
  - 받는 시각은 「오후 12시경」 뒤로 잡아야 합니다. 이는 장 마감 뒤 실행 규칙과 일일 수집 예약 시각에 영향을 주므로 승인 대상입니다.
  - 응답의 종목 순서와 요청 순서가 같은지, 10개 중 일부가 없을 때(거래정지 등) 어떻게 오는지는 문서에 없습니다. 실행 승인 뒤 첫 시험에서 확인합니다.
- **7-1과의 관계**: 복수종목 시세를 쓰면 매일 갱신이 약 670호출이 됩니다. 그러면 L0(6,049)에서도 하루 약 4,860호출(6,049 − 670 − 토큰 등)을 채우기에 쓸 수 있습니다. 상한 올리기는 채우기를 빨리 끝내는 데만 필요해집니다.
