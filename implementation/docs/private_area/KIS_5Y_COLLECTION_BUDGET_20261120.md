# KIS 5년 수집 요청 예산 (2026-11-20, 오너 승인 요청용)

이 문서는 KIS 일봉을 5년치로 채우는 데 드는 호출·회차·시간·토큰을 정리한다.
숫자는 모두 코드와 실제 1일차 실행 기록에서 읽었다. KIS 호출은 하지 않았다.

## 1. 대상

| 구분 | 개수 | 근거 |
| --- | --- | --- |
| Universe504 종목 | 504 | `universe/universe_codes_v1.json` (504개, 중복 없음) |
| 승인 ETF | 15 | `kis_collector.py`의 `ETFS`, Worker `KIS_ETFS`와 같은 15개 |
| 합계 | 519 | `targets()` |
| 지금 받아 둔 종목 | 517 | `data` 가지 `kis/status.json` (2026-11-14 실행) |
| 아직 못 받은 종목 | 2 | `NASDAQ:PSKY`, `NASDAQ:WBD` (거래소 후보 3개 모두 빈 응답) |

받아 둔 517종목은 최신 100거래일(대부분 2026-06-25 ~ 2026-11-13)을 원주가(MODP 0)와 조정 계열(MODP 1)로 하나씩 갖고 있다.

## 2. 5년에 필요한 페이지

- 5년은 약 1,260거래일이다. 일봉 호출 한 번은 100행을 준다.
- 1,260 ÷ 100 = 12.6 → 종목당 13페이지(1,300거래일)가 필요하다.
- 최신 1페이지는 이미 있다. 그래서 **더 오래된 페이지 12개**가 남았다.
- 원주가(MODP 0)는 기록이다. 12페이지 모두 MODP 0으로 받는다.
- 조정 계열(MODP 1)은 수집기 규칙상 **최신 페이지에만** 붙는다(`plan()`의 `modp1 and latest`). 오래된 페이지에는 MODP 1을 부르지 않는다. 새 규칙을 만들지 않는다.
- 상장 기간이 5년보다 짧은 종목은 중간에 빈 페이지가 와서 멈춘다(`history_end`, 실패 아님). 그래서 아래 호출 수는 상한이다.

## 3. 실제 속도 (2026-11-14 1일차 실행)

비공개 저장소 run 43651542034의 고정 로그 한 줄:
`calls=1042 seconds=817 pages=1040 ... rate_limited=0 failed=0 unresolved=2`

- 1호출에 평균 약 0.78초가 걸렸다. 초당 약 1.3건이다.
- 코드의 간격(`PACE = 0.2`, 초당 5건)은 하한일 뿐이다. 실제로는 응답 시간이 속도를 정한다.
- KIS 한도(계정당 초당 18건, 초당 25건에서 `EGW00201` 관측)보다 훨씬 느리다. 속도 제한에 걸릴 걱정은 작다.
- 기존 문서(KIS_COLLECTOR_20261114)의 "초당 5건" 시간 추정은 실제보다 약 4배 짧다.

## 4. 한 회차의 한계

| 한계 | 값 | 어디서 |
| --- | --- | --- |
| 오래된 페이지 수 | 회차당 최대 10 | `MAX_OLDER_PAGES = 10`, 워크플로 입력 `older_pages` 0~10 |
| 계획 호출 상한 | 8,000 | `MAX_CALLS` |
| 실행 중 호출 상한 | 2 + 계획 호출 × 2 | 워크플로 인라인 단계 `state['cap']` |
| 작업 시간 | 45분 | 워크플로 `timeout-minutes: 45` |

실제로 먼저 걸리는 것은 **45분**이다. 페이지 수 10이나 호출 8,000이 아니다.

- 45분을 넘기면 작업이 취소된다. 저장·커밋 단계는 `always() && !cancelled()` 조건이라 건너뛰어질 수 있다. 그러면 그 회차에 받은 페이지를 모두 잃고, 토큰 폐기도 못 할 수 있다.
- 그래서 받는 시간은 회차당 약 35분 안으로 잡는다. 받기 전 준비가 약 30초, 저장과 커밋이 1~3분 걸린다.

## 5. 회차별 예산 (오래된 페이지, 517종목)

호출 수 = 517 × 페이지 수(+ 토큰 발급·폐기 2). 시간 = 호출 수 × 0.78초.

| older_pages | 일봉 호출 | 계획 max_calls | 받는 시간 | 판단 |
| --- | --- | --- | --- | --- |
| 2 | 1,034 | 1,551 | 약 13.5분 | 안전 |
| 4 | 2,068 | 2,585 | 약 27분 | **권장** (1호출 1.16초까지 버팀) |
| 5 | 2,585 | 3,102 | 약 34분 | 여유 작음 |
| 6 | 3,102 | 3,619 | 약 40.5분 | 45분에 너무 가까움. 쓰지 않음 |
| 10 | 5,170 | 5,687 | 약 68분 | 45분 초과. 쓰지 않음 |
| 12 (한 번에) | 6,204 | — | 약 81분 | 지금 허용 안 됨, 45분 초과 |

계획 max_calls는 `plan()`에 실제 `coverage.json`을 넣어 계산했다(latest=no이면 종목마다 1을 더 세는 보수적 계산이다).

## 6. 권장 계획: 3회차 × older_pages=4

| 항목 | 값 |
| --- | --- |
| 회차 | 3회 (4 + 4 + 4 = 12페이지) |
| 회차 입력 | `mode=collect`, `latest=no`, `older_pages=4`, `modp1=no` |
| 회차당 일봉 호출 | 2,068 (+ 토큰 2) |
| 전체 일봉 호출 | 6,204 (+ 토큰 발급 3, 폐기 3) = KIS 요청 6,210 |
| 회차당 시간 | 받기 약 27분, 작업 전체 약 29~31분 |
| 전체 시간 | 받기 약 81분 |
| 토큰 | 3개 = 카카오톡 알림 3번 |
| 날짜 | 하루에 3회 이어서 가능(`concurrency: kis-token`이라 겹치지 않음). 3일에 나눠도 된다 |
| 결과 | 517종목 × 1,300거래일(약 2021년 9월부터, 상장이 더 늦은 종목은 상장일부터) |

- 다음 회차는 `coverage.json`의 가장 이른 날 앞에서 자동으로 이어 받는다. 같은 입력을 세 번 실행하면 된다.
- 첫 회차 뒤 로그의 `seconds=` 값을 본다. 1호출이 1.16초를 넘으면 남은 회차를 `older_pages=3`으로 줄인다.
- 1일차를 포함한 5년 전체: 일봉 7,244호출(1일차 1,040 + 6,204), 토큰 4개(이미 쓴 1개 포함).
- 다른 안: 5 + 5 + 2도 3회차다. 시간 여유가 작아서 4 + 4 + 4를 권한다. 2회차(6 + 6)는 45분에 너무 가까워 권하지 않는다.

## 7. 바꿔야 할 것

**코드 변경: 없음.** `kis_collector.py`의 `MAX_OLDER_PAGES = 10`과 `MAX_CALLS = 8000`은 4페이지 회차를 이미 허용한다. 이 브랜치는 코드를 바꾸지 않는다.

**비공개 워크플로 파일 변경: 없음.** 입력만 고른다. 실행 입력 한 줄:

```
mode=collect  latest=no  older_pages=4  modp1=no
```

이것을 3번 실행한다. (`modp1`은 latest=no이면 계획에서 꺼지지만, 혼동을 막으려고 no로 둔다.)

참고로, 한 번에 12페이지를 받으려면 두 가지를 같이 바꿔야 한다. 권하지 않는다.
- `kis_collector.py`: `MAX_OLDER_PAGES = 10` → `12`, 그리고 비공개 워크플로 `older_pages` 선택지에 `'11', '12'` 추가
- 비공개 워크플로: `timeout-minutes: 45` → 90 이상 (받는 데만 약 81분)
한 회차가 길수록 중간 실패 때 잃는 양이 커진다. 3회차가 더 안전하다.

## 8. 5년 뒤 매일 갱신 비용

최신 페이지만 받는다(`latest=yes`, `older_pages=0`).

| 입력 | 일봉 호출 | 시간 | 토큰 |
| --- | --- | --- | --- |
| modp1=yes | 약 1,040 (517×2 + 못 받은 2종목 후보 6) | 약 14분 (1일차 실측 817초) | 1개 = 알림 1번 |
| modp1=no | 약 523 | 약 7분 | 1개 = 알림 1번 |

- **정정 (2026-11-20 오너 확인):** 앞의 초안은 「매일 최신 100거래일 페이지를 새 파일로 쌓는다」고 적었다. 이것은 틀렸다. 정해진 방식(11/17 B2, 11/19 세 번째 안)은 **겹치는 원문을 Git에 두지 않고, 새로 들어온 행과 원문 해시만 남긴다**이다(Codex #571 `kis_stock_journal append`: `rows/`·`captures/`).
  - 매일 받은 100거래일 페이지는 실행기 임시 폴더에만 두고 `data` 가지에 커밋하지 않는다. `append`가 그중 새 행과 해시만 일지에 더한다.
  - 지금 수집 워크플로(`kis-daily-collect.yml`)의 `latest=yes`는 페이지를 `data` 가지에 커밋한다. 그래서 **매일 자동 수집은 이 방식이 고쳐질 때까지 켜지 않는다.** 1일차(11/14) 한 번만 그렇게 커밋됐다.
  - 고치려면 매일 쓰는 요청 파일을 만드는 방법이 있어야 한다(Codex #437 Q1). 그 답을 받은 뒤 수집과 게시를 한 흐름으로 잇고, 키가 있는 단계는 수집 하나로 둔다.
- 5년치 오래된 페이지(이 문서 7절)는 서로 겹치지 않는 처음 한 번의 원문이다. Codex 예산의 「처음 5년 원문」 몫에 해당한다. 이 원문을 일지에 넣은 뒤에도 페이지 파일을 Git에 둘지는 Codex Q2에 함께 물었다. 지우거나 다시 쓰지는 않는다.
- 갱신을 100거래일 넘게 쉬면 사이가 빈다. 그때는 따로 요청한다.

## 9. 그대로 두는 것

- 멈춤 규칙은 바꾸지 않는다: 재시도 뒤에도 실패한 페이지 25개 초과(`MAX_FAILED`), 속도 제한 응답 60개 초과(`MAX_RATE_LIMITED`), 인증 실패(401·403, `EGW00121`·`EGW00123`), 호출 상한, 공개 고정 커밋이 기본 가지의 조상이 아닐 때, 저장 검사 거부.
- 주문·계좌·잔고 경로는 없다. 허용 경로는 토큰 발급·폐기·해외 기간별 일봉 셋뿐이다.
- 키는 비공개 저장소 Secret에만 있다. 키가 있는 단계는 인라인 스크립트 하나뿐이다.
- 로그에는 개수·짧은 코드·날짜만 남는다.
