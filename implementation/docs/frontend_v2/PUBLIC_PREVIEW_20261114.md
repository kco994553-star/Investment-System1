# 새 앱 공개 미리보기 게시안 (2026-11-14, Main)

근거: DC-51(한 번에 전환하지 않고 단계 게시), 오너 2026-11-14 승인 「새 앱 미리보기는 누구나 볼 수 있는 공개 주소로 게시해도 된다.
공개 부분(검색, Q·G, 리더보드 등)은 공개 자료만 쓰고, 비공개 칸(KIS, 내 시트 V)은 로그인·연결 전에는 "준비 중" 또는 "로그인 필요"로만
보이게 한다」.
이 문서와 PR은 게시안이다. **병합 = 다음 Pages 배포부터 게시**이므로 병합·배포는 오너 승인 뒤에만 한다.

## 1. 무엇이 어디에 게시되나

- 주소: 지금 사이트 옆 `app.html` (`…/Investment-System1/app.html`). 지금 화면 `index.html`은 바이트 그대로다.
- 만드는 곳: `tools/web_app_preview.py` `emit()`. `build_pages_cockpit.py`가 마지막에 부른다. 그래서 Pages를 만드는 두 워크플로
  (`sec-daily-public-inputs.yml` 야간, `cockpit-pages.yml` 수동)가 같은 결과를 낸다. 워크플로 파일은 바꾸지 않았다.
- 무엇을 더하나 (39개, 모두 산출물 맨 위 폴더):
  - `app.html`: `web_app/index.html`에 세 가지만 더한 것: 배너 `새 화면 미리보기 · 일부 기능 준비 중` + 기존 화면 링크
    (홈 `./#home` · 리더보드 `./#leaderboard` · 기술적 분석 `./#technical` · 포트폴리오 `./#portfolio`), 배너 스타일 링크,
    `screen-detail.js` 대신 `app-screen-detail.js`.
  - `preview-banner.css`: 배너 스타일(`product/web_preview/`).
  - `app-screen-detail.js`: 새 앱의 `screen-detail.js`. 지금 사이트에 같은 이름의 다른 파일이 있어 이름만 바꿔 게시한다.
  - 새 앱 파일 36개(`action.js` … `tech-screen.js`).
- 더하지 않는 것:
  - 새 앱이 다시 쓰는 옛 모듈 61개: 지금 사이트의 같은 파일을 그대로 읽는다. 바이트가 다르면 빌드가 실패한다.
  - 글꼴 `jua-regular-ksx1001.woff2`·`jua-OFL.txt`: 지금 사이트 파일과 같은 바이트라 함께 쓴다.
  - 공개 자료(JSON): 새로 쓰는 것이 없다. `data.js`가 지금 사이트 자료를 이름으로 읽는다.
- 이름 충돌 처리: 지금 사이트 파일을 덮어쓸 일이 생기면(같은 이름, 다른 내용) 빌드가 실패한다. 덮어쓰지 않는다.
- 서비스 워커·오프라인 캐시: 지금 사이트에도 없고(라이브 `sw.js` 404) 미리보기에도 없다.
- 보안 정책(CSP): `app.html`의 CSP는 새 앱 `index.html`과 같고, 그것은 지금 `index.html`과 같다(기존 시험). 인라인 스크립트 없음.

## 2. 파일 수·크기 (가드 한도는 그대로)

| 항목 | 값 |
| --- | --- |
| 가드 한도 | 192개 · 파일당 2 MiB · 이름·SHA-256 고정 (바꾸지 않음) |
| 로컬 빌드 (공개 자료 일부만) | 137 → **176** (+39) |
| 실제 배포 추정 (라이브 공개 자료 7개 추가) | 144 → **183** (여유 9) |
| 라이브 공개 자료를 받아 넣은 빌드의 가드 결과 | PASS, 183개 |
| 가장 큰 새 파일 | `jua-regular-ksx1001.woff2` 187,292 B (공유, 새로 더하지 않음) |

- 가드: `pages_artifact_guard.py` `APPROVED_SHA256`에 39개 이름·해시를 더했다. 한도·검사 항목·예외는 바꾸지 않았다.
  새 앱 파일이 바뀌면 같은 PR에서 고정값을 다시 맞춘다(옛 화면 파일과 같은 규칙).
- **앞으로의 한계:** 화면 묶음 #538(→#536→#533→#530→#526→#522)이 들어오면 새 앱 파일이 70개가 되어 미리보기가 약 +69개,
  배포 약 213개로 192를 넘는다. 그대로 두면 가드가 배포 전체를 막는다(야간 공개 자료 배포 포함).
  - 막는 장치: `tests/test_web_app_preview.py`가 "로컬 빌드 + 허용 목록에 있으나 로컬 빌드에 없는 공개 자료(라이브 전용, 지금 7개) ≤ 192"를 확인한다.
    넘치는 PR은 CI에서 먼저 실패한다.
  - 대책 (그 PR에서 오너에게 고르게 함):
    - (가) 첫 화면 스크립트를 미리보기 빌드에서 한 파일로 묶기: 순서는 같고, 한 파일 오류가 뒤 파일을 멈추는 차이가 있음.
    - (나) 그 시점에 정식 전환 단계로 넘어가기.
    - 한도를 올리는 안은 지시상 쓰지 않는다.

## 3. 공개·비공개 경계 (시험으로 확인)

`tools/web_app_preview_browser_test.js`가 실제 Pages 빌드를 띄워 320·390·1440 px에서 확인한다(177항목 통과).
- 메뉴 9개 전부에서 비공개 칸은 `비공개 기능 준비 중`(NOT_READY) 또는 `로그인 필요`(LOGIN_REQUIRED)만 보인다. READY는 없다.
  - 비공개 칸이 있는 화면: 기술적 분석 2 · 매크로 2 · 뉴스 1 · Lab 2.
- 로그인 전에는 다른 주소로 요청이 0건이다(구글 로그인 스크립트·Worker 포함).
  - 구글 스크립트는 「① 구글 로그인 준비」를 누를 때만 불린다(지금 사이트와 같은 방식).
- 로그인 전 RAM 가격 요소 0개, 시트 가격 버튼은 꺼짐.
- 화면을 열고 메뉴를 옮겨도 기기 저장(localStorage·sessionStorage·IndexedDB)은 0이다.
- 페이지 오류 없음. 콘솔 오류는 라이브 전용 공개 자료의 404뿐이다(로컬 빌드). 가로 넘침 없음.
- 지금 화면 `index.html`에는 배너도, 새 앱 셸도 없다.

글자 그대로 확인할 점:
- 아직 안 만든 칸은 새 앱 공통 문구 `연결 전`(= 준비 중)으로 보인다. 포트폴리오 5.1~5.4, QGV 1.2~1.5, 세부 화면이 여기에 해당한다.
- QGV 화면의 기존 「시총 순위(M3)용 가격 불러오기」 묶음은 로그인 전에 `연결 전 · ① 구글 로그인 준비 · ② 로그인`으로 보인다.
  이것이 이 묶음의 "로그인 필요" 상태다. 가격은 누를 때만, 이 기기 RAM에만 둔다.
  - 이 기능은 지금 사이트에도 있다. 같은 구글 로그인 허용 주소(Pages)에서 같은 방식으로 작동한다.
- 「내 시트 V」(DC-50)는 이 게시본에 아직 없다(#538 쪽 작업). 들어오기 전까지는 화면에 칸이 없다.

## 6. 배포·되돌리기

- 병합하면 다음 야간 `sec-daily-public-inputs.yml` 배포부터 `app.html`이 올라간다.
  - 바로 보려면 `cockpit-pages.yml` 수동 실행(오너 승인)으로 올린다.
- 배포 직전 가드(`pages_artifact_guard.py`)와 신선도 가드는 그대로 돈다. 미리보기 파일도 같은 가드를 지난다.
- 되돌리기: 이 PR을 되돌리는 PR 1개. 지금 화면 파일은 건드리지 않았으므로 되돌려도 지금 화면은 같다.
- 실기기 확인: 컨테이너 시험은 Chromium 에뮬레이션이다. 실제 iPhone Safari 확인은 게시 뒤 오너 기기에서 한다(아직 하지 않음).
