## Recommended decision

Main can decide all six operational dispositions below under CDR-015, as narrowed by CDR-016/017/018. None requires asking the user now. They authorize bounded tooling, evidence and owner routing; they do not close unproved acceptance. Preserve the raw tool result exactly, but keep `INTEGRATION_ACCEPTANCE=BLOCKED` while required authentication, execution coverage, attribution or exact-subject evidence is missing. A disclosed nonclaim is not a passed requirement.

CDR-014 §4 authenticates references; §7 requires executed/audited source agreement and verified runtime/provenance; §5 derives projection from existing ownership rather than inventing Frozen meaning; §9 requires actual merge-result audit. CDR-015 explicitly prohibits folding undetected/unverified scope into overall PASS. These are the basis for conservative implementation, not new numerical policy.

## Concrete current implementation findings

1. `.github/workflows/track-c-fpia.yml` checks out `${{ github.event.pull_request.head.sha || github.sha }}` and executes `implementation/tools/integration/track_c_fpia.py` from that checkout. This is appropriate candidate-tool CI, but the subject can supply the verifier; it does not by itself satisfy trusted-verifier role separation. The workflow has actions pinned to major tags and installs version-pinned runtime packages; versions alone do not establish immutable artifact provenance.

2. `track_c_fpia.py:verifier_provenance` records HEAD, file blobs and clean checkout. Its runtime check rejects dirty files. That proves recorded-byte consistency, not that the revision was independently authorized. `run_sha256` is explicitly integrity rather than authentication. An external authority/output anchor is necessary to avoid a self-consistent substituted verifier and forged output.

3. `track_c_fpia_workflows.py:VerifierSelf` currently treats files matching current or any historical blob in the verifier checkout as self-placement, excluding them from content scanning. An exact current verifier pin does not automatically authenticate every historical exempted version. Prefer a manifest of independently accepted self-artifact identities or a proof that broader historical exemptions cannot affect execution; absent that proof, keep acceptance blocked. Do not silently accept old vulnerable code as trusted self code.

4. `track_c_fpia.py:compose` includes authority, runtime, historical identity, projection, interference, v2 and regression, but does not itself gate on the separately reported dynamic/external nonclaims. `open_non_claims` adds disclosure text. Thus raw `FPIA_PASS` can coexist with incomplete scope. Keep that historical raw result and explicitly block the higher integration acceptance; implement an additive gate with new evidence rather than rewrite historical runs as if they already enforced it.

5. `track_c_fpia_checks.py:workflow_spoof` documents job collisions as notes. Actual code first executes `if not reasons: continue`, then computes collision only for already-failing unattributed cases. Therefore a pure collision may not even receive an independent diagnostic in the current record. A bounded diagnostic repair plus authenticated receipt binding is justified. Rejecting all generic collisions is unnecessary and obscures the actual evidence-substitution threat.

6. `track_c_fpia_checks.py:complement_static` rejects unattributed complement importers of TrackC at AC21. PR28 is a412-file audit/evidence branch with Python probes and copied evidence. Its author-owned provenance does not automatically make importing scripts part of authenticated R/V or trusted verifier. Keep the finding until the exact affected paths and their intended runtime role are checked. Optional evidence can remain on its immutable branch while code integration proceeds without it; this does not delete or rewrite historical evidence.

7. Current PR trigger is all pull requests, but job execution is guarded by base/head prefix `integration/`; dispatch always runs. The scope comment calls G7 pending. That prefix is a routing heuristic, not proof of TrackC content or applicability, and can miss an applicable candidate under another name. Branch-independent selector/classification is an autonomous integration-tooling repair. Final merge-result audit remains distinct from existing PR-head CI.

## Small decision-record shape

Each PIW decision may record: ID; CDR015 delegated authority and CDR016–018 limits; exact inputSHA/path; chosen disposition; alternative rejected; why; acceptance obligations; verification evidence; explicit unknowns; affected subjects; rollback to the previous tool revision/status without deleting old evidence. Keep implementation status, CI, independent review, adversarial review, coverage, governance closure, GIE closure and exact merge-result acceptance separate.

Recommended current status for the decision round: `D2_DISPOSITIONS_DECIDED / IMPLEMENTATION_AND_EVIDENCE_PENDING / INTEGRATION_ACCEPTANCE_BLOCKED`. Closing the old *decision-question* labels does not close the associated technical/evidence gates. Do not call them USER_D3_REQUIRED merely because their names contain D3.

The implementable scope is additive Integration/FPIA tooling, trusted harness separation, output-consumer identity, explicit coverage/applicability gates, finite counterexamples, independent verification and owner routing. No user escalation is needed to do those. If satisfying a future gate truly requires a Frozen semantic change, PIT relaxation, canonical merge, protected owner contract mutation, Holdout, Official/LIVE, real account/production-auth activation or payment, stop only that action and request the corresponding exact authorization. Do not request advance permission for hypothetical changes or for already authorized conservative repairs.
